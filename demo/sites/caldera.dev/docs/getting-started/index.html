Getting started

Ship your first release to Caldera’s global edge in under five minutes. This guide walks you through installing the CLI, linking a project and deploying to production — with preview environments and instant rollbacks included.

6 min read Updated Sep 30, 2026

Before you begin

You’ll need three things. If you already deploy somewhere else, you probably have them.

  • A Caldera account. The Hobby plan is free and includes three projects and unlimited previews.
  • Node.js 20 or later, if you install the CLI with npm. The Homebrew and curl installers have no dependencies.
  • A project with a build step that outputs static files or a server bundle. Caldera detects most frameworks on its own.

  1. Install the CLI

    The caldera CLI is a single binary for macOS, Linux and Windows. Install it with whichever package manager you already use:

    $ npm install -g @caldera/cli
    $ brew install caldera-dev/tap/caldera
    $ curl -fsSL https://caldera.dev/install.sh | sh

    Then confirm it’s on your PATH:

    zsh
    $ caldera --version
caldera 3.2.0 (darwin-arm64, built 2026-09-24)

  2. Log in

    Authenticate once per machine. caldera login opens your browser, asks you to confirm a one-time code, and stores a scoped token in the system keychain.

    zsh
    $ caldera login
  Opening https://caldera.dev/device in your browser…
  Your one-time code is KMRX-4Q7D

  ✓ Logged in as tess@harborlabs.dev (team: harbor-labs)

    Deploying from CI?Skip caldera login and set CALDERA_TOKEN instead. Create a deploy-only token under Team settings → Tokens; it can ship releases but can’t read secrets or change billing.

  3. Initialize your project

    From your project’s root, run caldera init. It detects your framework and build command, picks the edges nearest your users, and writes a caldera.toml.

    ~/code/ember-shop
    $ caldera init
  ? Project name   ember-shop
  ? Build command  npm run build  (detected from package.json)
  ? Output folder  dist
  ? Regions        auto  → lis1, fra1, iad1, sfo1, nrt1, syd1

  ✓ Wrote caldera.toml
  ✓ Linked to harbor-labs/ember-shop

    The generated file is short and readable. Commit it alongside your code — it’s the single source of truth for how your app builds and where it runs.

    caldera.tomltoml
    1name    = "ember-shop"
2regions = ["lis1", "fra1", "iad1", "sfo1", "nrt1", "syd1"]
3
4[build]
5command = "npm run build"
6output  = "dist"
7
8[previews]
9enabled = true
10ttl     = "7d"        # tear down previews idle for a week
11
12[health]
13path     = "/healthz"
14interval = 10          # seconds between checks, per edge

  4. Deploy to the edge

    Ship a production release with --prod. Caldera builds in an isolated runner, uploads immutable assets, then promotes the release on every edge at once. Traffic switches atomically, so no one ever sees a half-deployed app.

    ~/code/ember-shop
    $ caldera deploy --prod

  ◆ Caldera 3.2.0 · harbor-labs/ember-shop · main@3f9c2a1

  Build    ✓ Compiled 14 routes in 4.2s     312 kB
  Upload   ✓ 38 files, 1.8 MB              0.9s
  Edges    ✓ lis1  ✓ fra1  ✓ iad1  ✓ sfo1  ✓ nrt1  ✓ syd1
  Health   ✓ /healthz 200 on 6 of 6 edges

  ✓ Production  https://ember-shop.caldera.app  [11.6s]
    Release     rel_7Hq2xK

    Your app is now live on six edges. Run caldera open to see it, or stream requests from every region as they arrive with caldera logs -f.

  5. Open a preview

    Leave off --prod and you get a preview environment for every branch: an isolated copy of your app with its own URL, secrets scope and logs. Previews never receive production traffic, and they go to sleep when nobody is looking.

    ~/code/ember-shop
    $ git switch -c checkout-redesign
$ caldera deploy

  ✓ Preview  https://ember-shop-checkout-redesign.caldera.app  [9.8s]
    Sleeps after 30 min idle · expires in 7 days

Roll back a release

Every deploy creates an immutable release. Caldera keeps your last 20 releases warm on every edge, so rolling back is a pointer swap: it completes worldwide in under a second, with no rebuild.

Releases ember-shop
ProductionPreviewsAll
Add express checkout to cart drawerrel_7Hq2xKmain · 3f9c2a1
Production11.6sTB2m ago
Fix rounding on multi-currency totalsrel_5Mn8pWmain · a81d0e4

Serve product images as AVIF by defaultrel_2Lt4bRmain · 77be91c
Ready12.3sJOYesterday
Move product search to the edgerel_9Vc1aEmain · c04f7d2
Ready14.0sMKOct 4

Roll back from the dashboard, or from your terminal with the release ID:

zsh
$ caldera rollback rel_5Mn8pW

  ✓ Production now serving rel_5Mn8pW on 6 edges  [0.4s]
    Undo with: caldera rollback --undo

Rollbacks restore code and config, not data.If a release ran a database migration, make sure the previous release still works against the new schema before you roll back. Expand-then-contract migrations keep this safe.

Configuration reference

The keys you’ll reach for first. Every key is optional except name; anything you leave out falls back to what Caldera detects.

KeyTypeDefaultDescription
namestring—Project slug, unique within your team. Used in every URL.
regionsstring[]["auto"]Edges to deploy to. auto picks the six nearest your traffic.
build.commandstringdetectedShell command that produces your output folder.
build.outputstring"dist"Folder uploaded as the release’s immutable assets.
previews.ttlduration"7d"How long an idle preview environment lives.
health.pathstring"/healthz"Must return 200 on every edge before a release is promoted.

See the caldera.toml reference for all 40-odd keys, including canary weights and per-edge overrides.
